# 概要

BAMファイルは通常、ゲノム座標順にソートされるため、指定した領域のレコードを効率よく取得できる [@li2009sam]。しかし、secondary alignmentやsupplementary alignmentがあると、1つのリードに属するレコードが異なる座標に現れることがある。そのため、リードのすべての部分がどこにアラインされているかを調べるには、ゲノム座標ではなくQNAMEによってレコードを集める必要がある。

`qbix`は、座標順BAMファイルにQNAME検索を追加するサイドインデックスを作成する。インデックスには、QNAMEの固定幅ハッシュとBAMレコードの位置を格納する。検索時には、ハッシュから候補レコードを探し、BAM内の実際のQNAMEと照合する。インデックスは、メモリ効率のよい外部ソートによって構築できる。これにより、特定のリードについてすべてのアラインメントを集め、リードを中心とした解析に利用できる。

# 必要性

複雑な構造変異の解析では、個々のリードを調べ、各部分がリファレンスゲノムのどこにマッピングされるかを正確に特定する必要がある。これは特にロングリードで重要である。たとえば、同じQNAMEを持つすべてのアラインメントレコードを集めることで、キメラリードの各セグメントのゲノム上の位置が明らかになる。

QNAME検索は、ゲノム領域の解析とリード中心の解析を橋渡しする。座標ベースの解析で注目すべきリードを抽出した後で、そのQNAMEによって、そのリードに属するすべてのBAMレコードを取得できる。これらのレコードは、候補配列への再アラインメント、局所アセンブリ、および同一リードが支持するゲノム領域間の関係の解析に利用できる。同じ取得方法は、ハプロタイプや塩基修飾パターンに基づいてグループ分けされたリードのアラインメントを集める場合にも役立つ。

`samtools view -N`は、QNAMEのリストに一致するレコードを抽出できる [@danecek2021twelve]。ただし、要求するリードが少数であっても、BAMファイル全体をスキャンしなければならない。そのため、大きなBAMファイルでは遅くなる。SAタグから補足アラインメントの位置を得られる場合もあるが、タグの有無はアライナーと設定に依存する。また、SAタグは同じQNAMEを持つすべてのレコードを一般に列挙する仕組みではない。`qbix`は、既存の座標順BAMファイルから候補レコードを探し、実際のQNAMEを照合して結果を返すよう設計されている。

# 関連分野の状況

座標順BAM用のインデックスであるBAIとCSIは、QNAMEによる検索をサポートしない。BAMファイルを名前順にソートした場合は、QNAMEに基づくインデックスを作成できる [@kojix2026bni]。しかし、多くのツールでは座標順BAMも必要になるため、両方を保存するとBAM本体を二重に保持することになる。

座標順BAMファイル向けの`bri`は、QNAME文字列全体とBGZF仮想オフセットを格納するインデックスである [@simpson2019bri]。Atlantoolは、QNAME全体とオフセットをBGZF圧縮データファイルに格納し、その上に疎な上位インデックスを配置する [@rath2025atlantool]。いずれもQNAME文字列そのものを検索キーとして保持する。

これに対し、`qbix`はQNAME文字列の代わりに固定幅ハッシュを保持するため、インデックスサイズはQNAMEの長さに依存しない。検索時には、ハッシュに対応するBGZF仮想オフセットからBAMレコードを読み出し、QNAMEが一致したレコードだけを返す。

# ソフトウェア設計

`qbix`は、ロングリードの座標順BAMに対するQNAME検索を主な対象とする。設計目標は、検索の高速化、インデックスの小型化、インデックス構築の高速化の3点である。QBIインデックスは、固定幅ハッシュから複数のBAMレコード位置を引く、1対多インデックスである。インデックスの構築には、固定幅レコードを用いたバケット方式の外部ソートを使用する。

## ハッシュによる検索

インデックスでは各QNAMEのXXH3-64ハッシュを、1つ以上のBGZF仮想オフセットに対応づける。BGZF仮想オフセットとは、圧縮ブロックの位置と、そのブロック内の非圧縮位置を組み合わせたBAM内の位置である。

検索キーにはQNAME文字列ではなくハッシュを使用する。検索キーの大きさはQNAMEの長さに依存しない。ハッシュ配列には、異なるハッシュ値が一度ずつ昇順に並ぶ。対応するオフセットは、ハッシュごとのまとまりとして一つの配列に格納する。

各ハッシュは、上位 `P` ビットのradixプレフィックスと、残りのハッシュサフィックスに分割される。radixディレクトリは、プレフィックスごとにサフィックス配列の範囲を記録する。検索時には、この範囲だけを二分探索する。このため、配列全体を二分探索する場合より比較回数が少ない。

同じハッシュに対応するオフセットは、オフセット配列内で連続している。別のビットベクトルで各グループの先頭を示す。rankディレクトリには、512ビット区画ごとのグループ境界の累積数を記録する。この情報を使って、目的の境界を含む区画を特定する。連続する二つのグループ境界から、対応するオフセット範囲を求める。

![QBIはハッシュ検索とオフセット取得を分離する。各セクションを論理的な検索順に示す。](figures/qbi-index-structure.png){width=100%}

`qbix`は、得られた仮想オフセットからhtslibを通じてBAMレコードを読み取る [@bonfield2021htslib]。ハッシュ衝突がある場合は、QNAMEが一致するレコードのみ出力する。

公開データと一般的な30倍WGSの条件から見積もると、ヒトWGSの異なるQNAME数は、ロングリードBAMで約200万〜1,000万、Illumina BAMで約3億〜4億である [@shumate2020ashkenazi; @illuminaDnaPrep]。64ビットハッシュが一様かつ独立に分布すると仮定した場合、少なくとも1組の異なるQNAMEが同じハッシュ値を持つ確率は、前者で約10⁻⁷〜10⁻⁶のオーダー、後者で約0.3〜0.4%となる。

## インデックス構築

インデックス構築では、BAMを1回走査し、固定幅の `(hash, offset)` レコードをハッシュ上位ビットに基づく一時バケットへ分配する。各バケットは独立に、また複数のバケットは並列にソートできる。ソート済みバケットを番号順に処理すると全体の `(hash, offset)` 順が得られるため、そのままQBIへ逐次書き込める。この方式は全レコードをメモリに保持する必要がない一方、一時ディスク領域と追加の入出力を必要とする。

# 評価

測定には、3つの公開HG002アラインメントBAMファイルから `samtools view -bh` で抽出した21番染色体のサブセットを使用した。対象はGIAB Illumina HiSeq 2x250 Novoalign、GIAB PacBio HiFi Revio 48x（BioProject PRJNA1028149）、およびONT Open DataのOxford Nanopore R10.4.1 SUPである。Illuminaの元ファイルのヘッダーは `SO:unsorted` と宣言していたため、測定前に染色体サブセットをSAMtoolsで再ソートした。生成されたBAMのサイズとレコード数は、Illuminaが1.52 GiBと11,145,955レコード、PacBio HiFiが962.3 MiBと133,605レコード、Oxford Nanoporeが4.90 GiBと545,839レコードであった。

ベンチマークは、AMD Ryzen 7 5700X（8コア、16スレッド）、60 GiB RAM、Samsung 870 QVO SATA SSDを搭載したUbuntu Linux 26.04上で、qbix 0.0.9、SAMtools/HTSlib 1.24、Atlantoolの `release-983975f` を用いて実行した。QBIは `P = 16`、BGZFスレッド1、ソートスレッド1、ソートメモリ設定512 MiB、バケットビット数8で構築した。インデックス値は3回の構築の中央値、検索値はseed 20260730で独立に生成した5組のクエリセットの中央値である。測定前にBAMを1回読み込んだが、ファイルシステムキャッシュは明示的にクリアしていない。タイマー分解能0.01秒未満の時間は `<0.01 s` と報告した。コマンド、マニフェスト、クエリのチェックサム、各反復の結果は `paper/work` のベンチマークワークフローに記録されている。

## エンドツーエンド検索

`qbix`はクエリ順またはBAM順で結果を出力する。前者は入力順を保ち、後者は候補オフセットをソートしてランダムシークを減らす。

スケーリング曲線は、インデックス検索とBAM全体のスキャンでコスト特性が異なることを示す。測定範囲全体で、qbixは最速または最速タイであった。存在するQNAME数に応じて処理時間が増加した一方、`samtools view -N` はクエリセットごとに入力全体をスキャンするため、ほぼ一定であった。Atlantoolも全体スキャンを回避したが、これらのデータセットではqbixより急速に増加した。

存在するQNAMEを10,000個検索した場合、BAM順モードによりqbixの時間は、Illuminaで0.89秒、PacBio HiFiで0.67秒、Oxford Nanoporeで1.47秒に短縮された。存在しないQNAMEを10,000個検索した場合、クエリ順の時間はそれぞれ `<0.01 s`、`<0.01 s`、0.01秒であった。対応するAtlantoolの時間は2.78秒、2.09秒、2.35秒であり、`samtools view -N` は4.86秒、3.83秒、16.94秒であった。

正確性は、レコード順とSAMオプショナルタグ順を正規化した後、完全な `samtools view -N` スキャンと比較して確認した。10,000 QNAMEセットについて、qbixのクエリ順、qbixのBAM順、Atlantool、SAMtoolsは、レコード数とSHA-256ハッシュが一致した。Illuminaは19,971レコードと `8ed699da...27d8e8`、PacBio HiFiは10,167レコードと `e414c34d...bd4b34`、Oxford Nanoporeは15,594レコードと `336cbbab...885d1` であった。存在しないQNAMEセットでは、4手法すべてが0レコードを返した。

# 研究インパクト声明

`qbix`は、座標ベースのアクセスに使用する座標順BAMを維持したまま、リード名検索を追加する。ゲノム領域で特定したリードの全アラインメントを、別のQNAME順BAMを用意することなく、下流解析に渡すことができる。

本稿は、外部での学術的採用を主張するものではない。現在の貢献は、文書化された1対多インデックス、BAMレベルでの正確なQNAME検証、メモリ効率のよい構築、再現可能な評価である。

# 利用可能性

`qbix`は[GitHub](https://github.com/kojix2/qbix)および[crates.io](https://crates.io/crates/qbix)でMITライセンスのもと公開されている。ビルド済みバイナリはGitHub Releasesで配布され、リリースはZenodo [@kojix2026qbix]にアーカイブされている。リポジトリにはQBI形式仕様、ベンチマークスクリプト、生の測定結果、テスト、使用例が含まれる。
