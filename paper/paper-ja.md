# 概要

BAMファイルは通常、ゲノム座標順にソートされるため、指定した領域のレコードを効率よく取得できる [@li2009sam]。しかし、secondary alignmentやsupplementary alignmentがあると、1つのリードに属するレコードが異なる座標に現れることがある。そのため、リード全体を調べるには、ゲノム位置ではなくQNAMEによってレコードを集めなければならない。

`qbix`はサイドインデックスによって、既存の座標順BAMファイルにQNAME検索を追加する。固定幅ハッシュで候補BAMレコードの位置を特定し、その後、実際のQNAMEを検証する。インデックスはメモリ効率のよい外部ソートで構築できる。これにより、あるゲノム領域で特定したリードのアラインメントを離れた座標から集め、詳細な検査、再アラインメント、局所アセンブリなど、リードを中心とした解析に利用できる。

# 必要性

座標ベースの解析では、関心のあるゲノム領域に存在するリードを特定することが多い。しかし次の段階では、そのリード全体を調べる必要がある。同じQNAMEを持つ別のレコードが、遠く離れたブレークポイント、別のマッピング、またはキメラアラインメントの別セグメントを表している可能性がある。これは、複雑な再構成やリファレンスゲノムに十分に表現されていない配列をまたぐ長鎖リードで特に重要である。

QNAME検索は、ゲノム領域の解析とリード中心の解析をつなぐ。座標ベースの解析で注目すべきリードを特定した後、そのQNAMEによって、そのリードに属するすべてのBAMレコードを取得できる。これらのレコードは、リードの詳細な検査、候補配列への再アラインメント、局所アセンブリ、リード--遺伝子座グラフの構築に利用できる。同じアクセス方法は、リードをハプロタイプや塩基修飾パターンでグループ化する場合にも役立つ。

`samtools view -N`は、QNAMEのリストに一致するレコードを抽出できる [@danecek2021twelve]。ただし、要求するリードが少数であっても、BAMファイル全体をスキャンしなければならない。そのため、大きなBAMファイルでは遅くなる。`qbix`は、既存の座標順BAMファイルから、指定されたQNAMEに属するすべてのレコードを取得するよう設計されている。

# 関連分野の状況

BAMで一般的に使われるインデックス形式であるBAIとCSIは、ゲノム座標をインデックス化するが、QNAMEはインデックス化しない。QNAME順BAMは、BAMファイル自体を利用する疎インデックスによってQNAME検索をサポートできる [@kojix2026bni]。しかし、BAMへの座標順入力を要求するツールが多いため、通常は座標順BAMも別途必要になる。

座標順BAMファイル向けには、`bri`がQNAME文字列全体とBGZF仮想オフセットを格納するインデックスを導入した [@simpson2019bri]。Atlantoolは、QNAME全体とオフセットをBGZF圧縮データファイルに格納し、その上に疎な上位インデックスを配置する [@rath2025atlantool]。

`qbix`も座標順BAMにサイドインデックスを追加するが、QNAME文字列全体は格納しない。各QNAMEを固定幅ハッシュで表し、候補レコードとBAM内の実際のQNAMEを照合する。各ハッシュは1回だけ格納し、対応するオフセットは別の配列に保持する。そのため、インデックスサイズはQNAMEの長さに依存せず、同じQNAMEに属する複数レコードについて検索キーが繰り返されることもない。

# ソフトウェア設計

## QBIインデックス構造

QBIファイルは128バイトのヘッダーと、radixディレクトリ、ハッシュサフィックス配列、グループ開始ビットベクトル、rankディレクトリ、オフセット配列という5つのデータセクションで構成される。ヘッダーには各セクションの位置とサイズ、BAMレコード数、ユニークハッシュ数、radixパラメータ、元BAMファイルの情報が記録される。

各64ビットQNAMEハッシュ `h` は、上位 `P` ビットからなるradixプレフィックスと、残りのビットからなるハッシュサフィックスに分割される。radixディレクトリは、各プレフィックスに対応するハッシュサフィックス配列の開始位置と終了位置を記録する。ハッシュサフィックス配列には、ユニークハッシュごとのサフィックスが、元の64ビットハッシュの順序で1回ずつ格納される。QBIは現在 `P = 8`、`P = 12`、`P = 16`をサポートしている。

オフセット配列には、BAMレコードごとに1つの64ビットBGZF仮想オフセットが格納される。オフセットはハッシュ順、次に各ハッシュグループ内の仮想オフセット順に並ぶ。1つのハッシュが複数のオフセットに対応することもある。

グループ開始ビットベクトルは、オフセット配列内の各ハッシュグループの開始を示す。各オフセットに1ビットを割り当て、グループの最初のオフセットを1、その他を0とする。最後のグループの終端を示すセンチネルビットも1つ追加される。rankディレクトリは、このビットベクトルに対する `select1` を高速化する。512ビットブロックごとに、そのブロックより前にあるセットビット数の累積値を格納し、`select1`は対象ブロックを特定した後、最大8個の64ビットワードだけを調べる。

![QBIはハッシュ検索とオフセット取得を分離する。各セクションを論理的な検索順に示す。](figures/qbi-index-structure.png){width=100%}

検索時、QNAMEハッシュはプレフィックスとサフィックスに分割される。radixディレクトリによってハッシュサフィックス配列の該当範囲を特定し、二分探索をその範囲に限定する。ハッシュが見つかると、グループ開始ビットベクトルとrankディレクトリによって、そのオフセットグループの開始位置と終了位置を得る。

`qbix`はhtslibを通じて候補BAMレコードを読み取り [@bonfield2021htslib]、実際のQNAMEを比較する。これにより、ハッシュ衝突が発生しても正しいレコードだけが返される。

## メモリ効率のよい構築

`qbix`はBAMファイルを1回スキャンし、固定幅の `(hash, offset)` レコードをハッシュ上位ビットに従って一時ファイルに分配する。各一時ファイルを独立にソートし、プレフィックス順に処理してQBIインデックスを構築する。そのため、ピークメモリ使用量はBAMレコード総数ではなく、一度にソートする最大バケットの大きさに主に依存する。

ソート済みレコードは1回だけ処理される。各オフセットを書き込み、ハッシュが変わった場合にだけサフィックスとグループ境界を記録する。rankディレクトリとradixディレクトリも、すべてのハッシュとオフセットをメモリに保持せず、同じパスで構築される。

## 検索とインターフェース

`qbix`は、クエリ順とBAM順の2つの出力モードを提供する。クエリ順モードはQNAMEを逐次読み取り、同じ順序で結果を出力する。BAM順モードは候補オフセットをソートし、多数のQNAMEを要求した場合のランダムシークを減らす。

QNAMEは引数、ファイル、標準入力から与えられ、結果はSAMまたはBAMとして出力される。`qbix`は重複クエリの除去、存在しないQNAMEの記録が可能で、Rust APIとC APIからも利用できる。

# 評価

測定には、3つの公開HG002アラインメントBAMファイルから `samtools view -bh` で抽出した21番染色体のサブセットを使用した。対象はGIAB Illumina HiSeq 2x250 Novoalign、GIAB PacBio HiFi Revio 48x（BioProject PRJNA1028149）、およびONT Open DataのOxford Nanopore R10.4.1 SUPである。Illuminaの元ファイルのヘッダーは `SO:unsorted` と宣言していたため、測定前に染色体サブセットをSAMtoolsで再ソートした。生成されたBAMのサイズとレコード数は、Illuminaが1.52 GiBと11,145,955レコード、PacBio HiFiが962.3 MiBと133,605レコード、Oxford Nanoporeが4.90 GiBと545,839レコードであった。

ベンチマークは、AMD Ryzen 7 5700X（8コア、16スレッド）、60 GiB RAM、Samsung 870 QVO SATA SSDを搭載したUbuntu Linux 26.04上で、qbix 0.0.9、SAMtools/HTSlib 1.24、Atlantoolの `release-983975f` を用いて実行した。QBIは `P = 16`、BGZFスレッド1、ソートスレッド1、ソートメモリ設定512 MiB、バケットビット数8で構築した。インデックス値は3回の構築の中央値、検索値はseed 20260730で独立に生成した5組のクエリセットの中央値である。測定前にBAMを1回読み込んだが、ファイルシステムキャッシュは明示的にクリアしていない。タイマー分解能0.01秒未満の時間は `<0.01 s` と報告した。コマンド、マニフェスト、クエリのチェックサム、各反復の結果は `paper/work` のベンチマークワークフローに記録されている。

存在するQNAMEを10,000個検索した場合、BAM順モードによりqbixの時間は、Illuminaで0.89秒、PacBio HiFiで0.67秒、Oxford Nanoporeで1.47秒に短縮された。存在しないQNAMEを10,000個検索した場合、クエリ順の時間はそれぞれ `<0.01 s`、`<0.01 s`、0.01秒であった。対応するAtlantoolの時間は2.78秒、2.09秒、2.35秒であり、`samtools view -N` は4.86秒、3.83秒、16.94秒であった。

正確性は、レコード順とSAMオプショナルタグ順を正規化した後、完全な `samtools view -N` スキャンと比較して確認した。10,000 QNAMEセットについて、qbixのクエリ順、qbixのBAM順、Atlantool、SAMtoolsは、レコード数とSHA-256ハッシュが一致した。Illuminaは19,971レコードと `8ed699da...27d8e8`、PacBio HiFiは10,167レコードと `e414c34d...bd4b34`、Oxford Nanoporeは15,594レコードと `336cbbab...885d1` であった。存在しないQNAMEセットでは、4手法すべてが0レコードを返した。

# 研究インパクト声明

`qbix`は、座標ベースのアクセスに使用する座標順BAMを維持したまま、リード名検索を追加する。ゲノム領域で特定したリードの全アラインメントを、別のQNAME順BAMを用意することなく、下流解析に渡すことができる。

本稿は、外部での学術的採用を主張するものではない。現在の貢献は、文書化された1対多インデックス、BAMレベルでの正確なQNAME検証、メモリ効率のよい構築、再現可能な評価である。

# 利用可能性

`qbix`は[GitHub](https://github.com/kojix2/qbix)および[crates.io](https://crates.io/crates/qbix)でMITライセンスのもと公開されている。ビルド済みバイナリはGitHub Releasesで配布され、リリースはZenodo [@kojix2026qbix]にアーカイブされている。リポジトリにはQBI形式仕様、ベンチマークスクリプト、生の測定結果、テスト、使用例が含まれる。
